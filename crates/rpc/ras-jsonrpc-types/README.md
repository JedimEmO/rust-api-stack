# ras-jsonrpc-types

JSON-RPC 2.0 wire types: requests, responses, errors and error codes.
The RAS JSON-RPC macros and runtime crates build on them,
and they work just as well in any other JSON-RPC client or server.

The crate depends on `serde`, `serde_json` and `ras-spec-components`,
which has no dependencies of its own. It has no Cargo features.

## Installation

```toml
[dependencies]
ras-jsonrpc-types = "0.3"
```

## Requests and responses

```rust
use ras_jsonrpc_types::{JsonRpcError, JsonRpcRequest, JsonRpcResponse};
use serde_json::json;

let request = JsonRpcRequest::new("subtract".to_string(), Some(json!([42, 23])), Some(json!(1)));

let success = JsonRpcResponse::success(json!(19), Some(json!(1)));

let failure = JsonRpcResponse::error(
    JsonRpcError::method_not_found("subtract"),
    Some(json!(1)),
);
```

On the wire these are the usual JSON-RPC 2.0 objects:

```json
{ "jsonrpc": "2.0", "method": "subtract", "params": [42, 23], "id": 1 }
{ "jsonrpc": "2.0", "result": 19, "id": 1 }
{ "jsonrpc": "2.0", "error": { "code": -32601, "message": "Method not found: subtract" }, "id": 1 }
```

## Missing fields and `null`

JSON-RPC gives a missing field and a `null` field different meanings,
and a plain `Option` field in serde cannot tell them apart.
`JsonRpcRequest` keeps them apart for `params` and `id`:

| JSON | Rust |
|---|---|
| field missing | `None` |
| `"id": null` | `Some(Value::Null)` |
| `"id": 1` | `Some(json!(1))` |

A request without an `id` is a notification; `is_notification()` returns `true`,
and the server must not answer it.
A request with `"id": null` is an ordinary request, answered with `"id": null`.

`JsonRpcResponse` always serializes `id`, as `null` when it is `None`,
because JSON-RPC 2.0 requires the member in every response.
An error response to a request whose id could not be read, such as a parse error, carries `"id": null`.

## Errors

`JsonRpcError` has a constructor for each code in `error_codes`:

| Code | Constant | Constructor | Message |
|---|---|---|---|
| -32700 | `PARSE_ERROR` | `parse_error()` | `Parse error` |
| -32600 | `INVALID_REQUEST` | `invalid_request()` | `Invalid Request` |
| -32601 | `METHOD_NOT_FOUND` | `method_not_found(method)` | `Method not found: <method>` |
| -32602 | `INVALID_PARAMS` | `invalid_params(details)` | `Invalid params` |
| -32603 | `INTERNAL_ERROR` | `internal_error(details)` | `Internal error` |
| -32001 | `AUTHENTICATION_REQUIRED` | `authentication_required()` | `Authentication required` |
| -32002 | `INSUFFICIENT_PERMISSIONS` | `insufficient_permissions(required)` | `Insufficient permissions` |
| -32003 | `TOKEN_EXPIRED` | `token_expired()` | `Token expired` |
| -32004 | `CSRF_VALIDATION_FAILED` | `csrf_validation_failed()` | `CSRF validation failed` |

The first five are the codes JSON-RPC 2.0 defines.
The other four are this project's codes for authentication and CSRF failures,
taken from the range JSON-RPC reserves for servers.

`invalid_params` and `internal_error` take a `details` string and discard it,
so internal detail cannot reach the client by accident.
Use `JsonRpcError::new(code, message, data)` when the client should see more.

`insufficient_permissions` puts the required permissions in `data` as `{ "required": [...] }`.
It never includes the permissions the caller holds,
because that would let any user list their own grants by calling protected methods.

## Errors a handler sends to the client

A handler generated by the RAS macros returns `Box<dyn Error + Send + Sync>`.
By default every such error reaches the client as `-32603 "Internal error"` with no detail,
so a database error or a stack of `?` cannot leak internals.

To send an error the client can act on, return a `PublicRpcError` directly:

```rust
use ras_jsonrpc_types::PublicRpcError;
use serde_json::json;

fn register() -> Result<(), Box<dyn std::error::Error + Send + Sync>> {
    Err(PublicRpcError::new(1001, "Email already registered")
        .with_data(json!({ "field": "email" }))
        .into())
}
```

Its code, message and data are sent as written, with two limits.

The first limit is the code.
JSON-RPC reserves `-32768..=-32000`, and this framework gives several codes there a meaning,
such as `-32001` for a missing login.
A handler may use any code outside that range, plus `-32602` for its own validation.
Any other code is logged and sent as `-32603`.
`handler_code_allowed` performs this check.

The second limit is that only the returned error counts.
The server checks whether the error the handler returned *is* a `PublicRpcError`.
It does not search the error's `source()` chain or look inside a wrapper.
A `PublicRpcError` wrapped inside another error type stays hidden;
to forward one, return it as the handler's error.

`HandlerErrorOutcome` is the classification the generated servers use.
`from_handler_error` sorts an error into `Public`, `ReservedCode` or `Hidden`,
and `into_error` gives the `JsonRpcError` to send.

## Spec generation errors

`SpecGenerationError` is re-exported from `ras-spec-components`.
The generated `try_generate_*_openrpc` functions return it
when a service's OpenRPC document cannot be built, for instance because an example fails to serialize.
