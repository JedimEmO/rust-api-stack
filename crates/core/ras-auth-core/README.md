# ras-auth-core

The authentication and authorization contract shared by the Rust Agent Stack service crates.
It defines how a request credential becomes an `AuthenticatedUser`,
how permission requirements are checked,
and how bearer tokens and cookies reach the server.

The REST, JSON-RPC, bidirectional JSON-RPC and file service macros all generate code against this crate,
and `ras-identity-session` implements its `AuthProvider` trait for JWT sessions.
You implement `AuthProvider` yourself when your tokens come from somewhere else.

## Installation

```toml
[dependencies]
ras-auth-core = "0.3"
```

Code generated by `rest_service!` and `file_service!` names `ras_auth_core` paths directly,
so a crate that uses those macros needs this dependency too.

## Implementing an auth provider

An `AuthProvider` turns a token string into an `AuthenticatedUser`, or rejects it.

```rust
use std::collections::HashSet;

use ras_auth_core::{AuthError, AuthFuture, AuthProvider, AuthenticatedUser};

struct MyAuthProvider;

impl AuthProvider for MyAuthProvider {
    fn authenticate(&self, token: String) -> AuthFuture<'_> {
        Box::pin(async move {
            if token != "valid-token" {
                return Err(AuthError::InvalidToken);
            }

            Ok(AuthenticatedUser {
                user_id: "user-123".to_string(),
                permissions: HashSet::from([
                    "read".to_string(),
                    "write".to_string(),
                ]),
                metadata: None,
            })
        })
    }
}
```

The trait also has a default `check_permissions` method.
It passes when the user holds every permission in the list it is given.
Override it when permissions depend on a tenant, a role hierarchy or an external policy service.

## Main items

- `AuthProvider`: validates a token and checks permissions.
- `AuthenticatedUser`: the user ID, a `HashSet<String>` of permissions, and optional JSON metadata.
- `AuthError`: `InvalidToken`, `TokenExpired`, `InsufficientPermissions`, `AuthenticationRequired` and `Internal`.
  It is deliberately not `Serialize`, because `InsufficientPermissions` carries the caller's full permission set.
- `AuthFuture` and `AuthResult`: the boxed future and result types `AuthProvider` returns.
- `Caller`: the caller of an `OPTIONAL_AUTH` route, either `Anonymous` or `Authenticated(AuthenticatedUser)`.
- `authorize_request` and `resolve_caller`: the request pipeline the generated REST and file servers run.
- `check_permission_groups` and `user_satisfies_permission_groups`: the permission check every generated service uses.
- `AuthTransportConfig`, `AuthCookieConfig` and `CsrfConfig`: how credentials travel over HTTP.
- `redact_sensitive_headers` and `sanitize_log_detail`: helpers that keep credentials and injected control characters out of logs.

## Permission groups

The service macros accept three auth levels:
`UNAUTHORIZED`, `OPTIONAL_AUTH` and `WITH_PERMISSIONS([...])`.

A `WITH_PERMISSIONS` requirement is a list of groups.
The user must hold every permission in at least one group;
`WITH_PERMISSIONS(["admin"] | ["read", "write"])` admits an admin, or a user with both `read` and `write`.
`WITH_PERMISSIONS([])` admits any authenticated user.
An empty group next to non-empty ones is not a blanket grant; the macros reject that shape at compile time,
and `check_permission_groups` ignores it.

`authorize_request` runs the full pipeline for a protected route:
extract the credential, check CSRF, call `AuthProvider::authenticate`, then check the permission groups.
Each failure maps to an `AuthorizeError` variant, which the generated code turns into a protocol response.

## Optional authentication

An `OPTIONAL_AUTH` route is public, but it identifies the caller when it can.
It is never rejected for authentication reasons,
and the handler receives a `Caller` as its first argument.

`resolve_caller` is the non-rejecting counterpart to `authorize_request`.
It runs the same credential extraction, CSRF check and `authenticate` call,
but every failure resolves to `Caller::Anonymous` instead of an error:

```rust
pub async fn resolve_caller<P: AuthProvider + ?Sized>(
    method: &str,
    headers: &HeaderMap,
    auth_transport: &AuthTransportConfig,
    auth_provider: Option<&P>,
) -> Caller;
```

A missing credential, an invalid or expired token, a missing auth provider,
and a cookie credential that fails CSRF on an unsafe method all become `Caller::Anonymous`.
A forged or stale credential therefore gains nothing; the request runs as the public path.
No permission check runs, because an `OPTIONAL_AUTH` route has no required groups.
The file service passes the same optional caller through `FileRequestContext`.

## Bearer and cookie credentials

`AuthProvider` always validates a token string.
`AuthTransportConfig` decides where that string comes from:

```rust
use ras_auth_core::{AuthCookieConfig, AuthTransportConfig, CsrfConfig};

let transport = AuthTransportConfig::default()
    .with_cookie(AuthCookieConfig::default())
    .with_csrf(CsrfConfig::default());
```

Bearer tokens are enabled by default.
When both `Authorization: Bearer ...` and the configured cookie are present, the bearer token wins.
A bearer header that is present but malformed fails the request; there is no fallback to the cookie.
A request carrying two cookies with the configured name is rejected as ambiguous.

Cookie auth always comes with CSRF protection,
because the browser attaches cookies to cross-site requests.
`with_cookie(...)` installs a default `CsrfConfig` when none is set,
so the `.with_csrf(...)` call above is optional.
`AuthTransportConfig::validate()` fails when a cookie transport has no CSRF config,
which covers configs built as struct literals.

### Session cookies

`AuthCookieConfig` builds `Set-Cookie` values for the session token:

```rust
use ras_auth_core::AuthCookieConfig;

fn cookie_headers(jwt: &str) -> Result<(), ras_auth_core::AuthTransportError> {
    let cookie = AuthCookieConfig::default();
    let set_cookie = cookie.session_cookie_header_value(jwt)?;
    let clear_cookie = cookie.clear_cookie_header_value()?;
    Ok(())
}
```

The default cookie is named `__Host-ras-session`
and is `HttpOnly`, `Secure`, `SameSite=Lax` and `Path=/`, with no `Domain`.
It sets no `Max-Age`, so it lasts for the browser session;
the token's own expiry still applies.
`validate()` enforces the `__Host-` and `__Secure-` prefix rules
and refuses `SameSite=None` without `Secure`.
`insecure_for_local_development()` drops `Secure` and the `__Host-` prefix;
use it only for local HTTP.

### CSRF

`CsrfConfig::default()` is a double-submit check.
Generate a random token per session,
set it with `csrf_cookie_header_value(token)` (cookie `__Host-ras-csrf`, readable by scripts),
and have the browser client echo the same value in the `x-ras-csrf` header.
The check runs only for cookie credentials on `POST`, `PUT`, `PATCH` and `DELETE`,
and compares the two values in constant time.
Bearer credentials and other methods are exempt.

`CsrfConfig::validate()` rejects CORS-safelisted and browser-controlled header names
such as `accept`, `content-type` and `cookie`.
Only a custom header forces the CORS preflight that makes the check meaningful.

Two weaker modes exist, and their names are meant to discourage casual use:

- `CsrfConfig::dangerous_header_presence_only(...)` requires only that the custom header is present.
  It is sound only behind a restrictive credentialed CORS policy.
- `CsrfConfig::dangerous_static_value(...)` compares the header against one process-wide value
  that is not bound to a session.

Pairing either mode with cookie auth logs a `tracing::warn!`.
`header_presence_only` and `with_expected_value` are deprecated aliases for them.
